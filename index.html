Contexto

¿Por qué normalizar?

La normalización de bases de datos es el proceso arquitectónico fundamental que transforma volumen caótico de información en una estructura lógica, eficiente y altamente escalable. Al aplicar un conjunto de reglas de diseño secuenciales, esta técnica no solo elimina la duplicación innecesaria de los datos, sino que blinda el sistema contra inconsistencias y errores de actualización, sentando los cimientos técnicos indispensables para que cualquier aplicación moderna opere de manera segura y confiable.

¿Que es la redundancia de datos?

La redundancia de datos es la "repetición innecesaria de la misma información" en distintas partes de una base de datos. Este problema no solo desperdicia espacio de almacenamiento, sino que genera graves inconsistencias: si un dato cambia, tendrías que actualizarlo en múltiples lugares al mismo tiempo, corriendo el riesgo de que el sistema termine con información contradictoria.

¿Qué son las anomalías de BD?

Las anomalías de base de datos son problemas que surgen cuando los datos están mal estructurados o duplicados. Estos problemas pueden causar inconsistencias en la información y dificultar el mantenimiento de la base de datos.

¿Qué es la integridad referencial?

La integridad referencial es una regla que asegura que las relaciones entre tablas en una base de datos sean consistentes. Implica que cualquier valor de clave externa en una tabla debe corresponder a un valor de clave primaria en la tabla relacionada.

Definición formal

La normalización de bases de datos es el proceso para organizar tablas y relaciones para eliminar la redundancia de datos lo que evita errores en una actualizacion. el diccionario de datos es un documento o repositorio que contiene metadatos la cual pueden ser nombres, tablas, tipos de datos, descripciones, etc....

Tipos de anomalías

Anomalía de Inserción

Ocurre cuando no se puede registrar un nuevo juego porque todavia no existe una venta asociada, ejemplo: Call of Duty Modern Warfare IV no puede almacenarse hasta que alguien lo compre

Anomalía de Actualización

Si el teléfono de Juan Pérez cambia, habría que modificarlo en todas las filas donde aparece. Si una fila no se actualiza, existirán datos inconsistentes.

Anomalía de Eliminación

Si se elimina la única venta de un juego, también podría perderse toda la información relacionada con ese juego.

Caso práctico

El caso: Expert Games

ExpertGames Cartagena es una tienda de videojuegos que almacena clientes, juegos, categorías y plataformas en una sola tabla. Esto genera redundancia, anomalías y dificultades para mantener la información actualizada.

Problema 1FN detectado

La tabla viola la Primera Forma Normal (1FN) porque el campo "Plataforma" almacena múltiples valores dentro de una misma celda, por ejemplo: "PS5, Xbox, PC". Esto impide que cada atributo sea atómico y dificulta las consultas, actualizaciones y búsquedas. Para cumplir la 1FN, cada plataforma debe almacenarse en un registro independiente.

Problema 2FN / 3FN detectado

Existen datos repetidos de clientes y videojuegos en varias filas. Por ejemplo, el nombre y teléfono de Juan Pérez aparecen cada vez que realiza una compra. Además, la categoría depende del juego y no directamente de la venta, generando una dependencia transitiva. Esto provoca redundancia de información, inconsistencias al actualizar datos y posibles anomalías de inserción, actualización y eliminación.

Proceso

Formas Normales

A continuación se muestra el proceso de normalización aplicado a la base de datos de ExpertGames Cartagena, transformando una tabla con redundancia en un modelo organizado en Tercera Forma Normal (3FN).

1°
Primera Forma Normal (1FN)
Todos los atributos deben contener valores atómicos y no pueden existir grupos repetitivos

La Primera Forma Normal busca que cada campo almacene un único valor. En nuestro caso, el atributo plataformas almacenaba varios valores en una misma celda.

1
Identificar atributos no atómicos

Se encontró que la columna plataformas contenía múltiples valores separados por comas.

2
Separar los valores repetidos

Cada plataforma se registró en una fila independiente para que cada campo contenga un único dato.

3
Verificar la atomicidad de los datos

Se comprobó que todas las columnas almacenaran únicamente un valor por registro.

2°
Segunda Forma Normal (2FN)
Todos los atributos deben depender completamente de la clave primaria

La 2FN exige que ningún atributo dependa parcialmente de la clave. Se separan las entidades en tablas independientes.

Dependencias parciales en la tabla

— nombre_juego depende solo de id_juego, no de id_venta.
— categoria depende solo de id_juego, no de id_venta.

3°
Tercera Forma Normal (3FN)
No deben existir dependencias transitivas entre atributos no clave

La 3FN elimina dependencias transitivas: atributos que dependen de otros atributos no clave. Se separa la categoría del juego en su propia tabla.

PostgreSQL · Modelo Final 3FN
-- Modelo final ExpertGames en 3FN

CREATE TABLE CATEGORIAS (
  id_categoria  VARCHAR(10)    PRIMARY KEY,
  nombre        VARCHAR(50)    NOT NULL
);

CREATE TABLE CLIENTES (
  id_cliente    VARCHAR(10)    PRIMARY KEY,
  nombre        VARCHAR(100)   NOT NULL,
  telefono      VARCHAR(15)    NOT NULL
);

CREATE TABLE JUEGOS (
  id_juego      VARCHAR(10)    PRIMARY KEY,
  nombre        VARCHAR(100)   NOT NULL,
  id_categoria  VARCHAR(10)    REFERENCES CATEGORIAS(id_categoria)
);

CREATE TABLE VENTAS (
  id_venta      SERIAL         PRIMARY KEY,
  id_cliente    VARCHAR(10)    REFERENCES CLIENTES(id_cliente),
  id_juego      VARCHAR(10)    REFERENCES JUEGOS(id_juego),
  fecha         DATE           DEFAULT CURRENT_DATE
);

CREATE TABLE VENTA_PLATAFORMAS (
  id_venta      INT            REFERENCES VENTAS(id_venta),
  plataforma    VARCHAR(30)    NOT NULL,
  PRIMARY KEY  (id_venta, plataforma)
);

Diccionario de Datos

Definición

Un "diccionario de datos" es un documento o repositorio que centraliza los metadatos de un sistema de información; es decir, define detalladamente la estructura, el significado, el tipo de dato, las restricciones y las relaciones de cada elemento en una base de datos. Su propósito principal es actuar como un manual de referencia compartido que garantiza la consistencia de la información, facilita el mantenimiento del sistema y asegura que tanto desarrolladores como analistas entiendan exactamente qué significa cada dato.

Cierre

Conclusiones del equipo

En resumen, aprendimos que la normalización es clave para ordenar una base de datos en tablas lógicas, evitando repetir datos y previniendo errores al modificarlos para que el sistema sea eficiente. Lo más difícil fue pasar la teoría a la práctica, sobre todo al descifrar las dependencias funcionales y decidir cómo dividir las tablas (como en la 3FN) sin romper las reglas de negocio. Finalmente, para aplicarlo en un proyecto real, lo ideal es diseñar un buen modelo entidad-relación desde el principio, lo que facilita la programación del backend (CRUD, consultas, ORM) y asegura que el software pueda crecer sin volverse lento ni inestable.

Lección de Stiven

La normalización es indispensable para estructurar bases de datos eficientes, lógicas y libres de datos duplicados. Dominar este proceso garantiza que el sistema no genere errores raros ni colapse cuando la información empiece a crecer.

Lección de erick

Diseñar una base de datos sólida requiere conectar la teoría con las reglas reales del negocio antes de tirar código. Aunque separar las tablas de forma lógica (como en la 3FN) sea un reto mental, es lo que evita dolores de cabeza al programar.

Lección de michael

Una estructura limpia y normalizada es el verdadero motor de un backend estable, rápido y fácil de mantener. Hacer este trabajo desde el principio facilita la creación de consultas SQL y permite que el proyecto sea escalable a futuro.
